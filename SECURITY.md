# Security design and limits

This is a small, self-hosted single-operator broadcaster. It has layered protections, but it has not undergone an independent penetration test or security certification.

## Layers implemented

| Layer | Concrete behavior |
| --- | --- |
| Private network | Recommended setup is Tailscale Serve, reachable only from the permitted private network. Node binds to loopback by default. No router port forwarding is needed. |
| Encrypted transport | Browser-to-relay uses HTTPS/WSS, with HTTP permitted only for localhost development. Platform outputs accept RTMPS only. FFmpeg certificate verification is enabled; a trusted CA file can be configured. |
| Long-term access | A 256-bit random relay secret is generated locally. Constant-time comparison verifies it. It is used only to establish a session. |
| Session isolation | Random session tokens live only in browser/server memory, expire after eight hours and are bound to the browser origin. Disconnect revokes them. Restarting the relay clears all sessions. |
| Upload authorization | Each upload needs a random, origin-bound, one-use ticket with a 30-second lifetime. The first WebSocket message carries it; keys/tokens do not appear in URLs. Replays fail. |
| CORS and CSRF boundary | Explicit allowed origins, no wildcard, no cookie authentication and no credentialed cross-origin fetches. Unknown origins are rejected at HTTP and WebSocket upgrade. |
| Same-origin session binding | API requests include `X-MK97-Origin` because same-origin browser GETs can omit `Origin`. Both headers, when present, must identify the same allowed origin. The client header never overrides a browser Origin; a bearer token is still required. This allows a website served by its own relay to keep its session without accepting a conflicting origin claim. |
| Resource limits | One active broadcaster, eight connections/sessions, 24 pending tickets, authentication/HTTP rate limits, five-second WebSocket authentication deadline, 16 MB message ceiling, bounded upload buffers, ingestion-rate and inactivity limits. Ordinary JSON bodies are capped at 4 KB; OAuth completion allows 8 KB and YouTube metadata 16 KB. Google responses are capped at 1 MB and requests time out. |
| Replay limits | JPEG ring limited by duration and bytes (default 30 seconds / 192 MB); PCM ring separately bounded, frames capped, graphics cache capped at 16 entries, event queue capped at 12, pending boundary windows at two. Up to three clips with a shared 64 MB logical size limit. FFmpeg/process overhead is additional. |
| Clip isolation | Clips use random identifiers, stay in laptop RAM and require the session owning the active broadcast. Authentication in headers, no public clip URLs, no-store responses, one export process at a time, 30-second export limit. Stop/logout terminates an active export. The relay has no video recording directory. |
| Secret containment | Manual keys and the Google client secret stay in the laptop's untracked `.env`; Google access/refresh tokens and generated stream keys stay in session-scoped relay memory. API responses expose channel/event metadata and public watch links, never ingestion URLs/keys or Google tokens. Raw FFmpeg stderr is not emitted. |
| Google authorization | Authorization code flow with a five-minute, random one-use state bound to relay session and frontend origin, S256 PKCE and a server-side client secret. Callback messages require the exact popup/origin/state or a same-origin channel named with the random one-use state. This channel also works when browser isolation removes the popup opener. The callback removes its code from the visible URL and makes no third-party asset requests. Completion still requires relay bearer authorization. |
| Account lifecycle | Pending sign-in suppresses older YouTube destinations. Cancellation/logout/session expiry clears pending flows; an in-flight cancelled callback cannot restore a connection. Explicit disconnect attempts Google revocation. Refresh tokens are kept only for the in-memory session and refresh calls are deduplicated. |
| Event control | Broadcast IDs and RTMPS destinations come from Google responses, not phone-supplied targets. Creation is idempotent for the same request/details. Ambiguous writes require Studio review before a new setup. Go live requires an active signal; publication/end are explicit controls. No event deletion API is exposed. |
| Output restrictions | Only RTMPS endpoints on expected platform subdomains are accepted. File URLs, private IP destinations, credentialed server URLs and tee-injection separators are rejected. Destinations cannot be supplied by the phone. |
| Media isolation | Uploads are treated as binary media, use explicit MOV or Matroska demuxers and permit only the `pipe` input protocol. Input media cannot ask FFmpeg to fetch arbitrary network/file URLs. Child processes use argument arrays without a shell. |
| Score isolation | The phone supplies numeric IDs, never an arbitrary upstream URL. Custom score endpoints are trusted operator configuration, use HTTPS, time out, and have a 2 MB response ceiling. Returned data is whitelisted and length bounded. Raw player records/emails are not returned. |
| HTML scorecard boundary | Fixed CricClubs HTTPS host/read-only path, numeric IDs and bounded league names; no redirects, cookies or scripts. robots.txt and crawl-delay are honored. Body/row/cache limits and request deduplication apply. Verification/401/403 stops full-card reads for the relay session; rate limits/unavailability pause them. Only whitelisted text is exposed, and source identity/totals must match the ticker before enrichment. Background reads cannot block the camera/ticker path. |
| Rendering protections | No third-party JS, fonts or analytics; local modules only. Text uses `textContent`, not HTML insertion. Local SVG templates XML-escape all feed values and accept no user SVG, scripts, styles or image URLs. A pinned native renderer generates PNGs locally. FFmpeg score text disables expansion. CSP, referrer suppression, anti-framing headers on the relay and no-store API responses are provided. |
| Publishing boundary | GitHub Pages workflow publishes `web/` only. No environment file, node_modules, API or relay state is deployed. |

## Operator responsibilities and boundaries

- Protect the laptop account, disk, platform accounts and private Tailscale network with appropriate device security and MFA. An attacker with control of the laptop can read `.env`, memory and process state. RTMPS destination URLs can be visible to local process-inspection tools because FFmpeg needs them as arguments.
- Use current FFmpeg/Node/Tailscale builds. FFmpeg parses complex media; this app does not provide an OS sandbox around it. Keeping the relay private and patched is part of the design.
- Access to the long-term relay token grants broadcast control. There is one operator role, without multi-user RBAC, approval workflows or per-user audit history. This app is not a public SaaS service.
- GitHub Pages cannot set all custom HTTP response headers. A CSP meta tag restricts the frontend, but `frame-ancestors`/HSTS/X-Frame-Options for that public origin depend on its host. The relay itself sends anti-framing/security headers. Use the private same-origin site or a host you control if you require custom headers everywhere.
- GitHub projects can share an origin. Do not host untrusted scripts on your account's other Pages projects. No master/session/platform secrets are saved to localStorage; only the relay address, match ID, club ID and operator-provided public viewing link are remembered.
- The obsolete build's `boundary.ytKey` localStorage entry is removed at startup. New platform connections require relay configuration or Google's OAuth flow; a typed account name cannot authorize a destination.
- Public score preview sends only validated numeric identifiers to a fixed CricClubs HTTPS read endpoint, with credentials omitted, no referrer, redirects refused and a 2 MB decoded-body limit. It cannot request arbitrary source URLs. After relay connection, preview uses the encoder's relay snapshot. Full-card rows and commentary remain whitelisted plain data, with no HTML rendering or inferred scorecard fallback.
- The Google scope permits YouTube management because the Live Streaming API needs it. The UI does not ask for Gmail/Drive access, but the Google consent grant is still sensitive. Keep your Cloud client and host under your control. A successful application logout clears local memory; use Disconnect account or Google's account controls when you also want to revoke its external grant.
- Private-network reachability and CORS are different controls. CORS is not a network firewall. Private Serve supplies that outer network boundary; the application still checks its own authentication.
- The public score reader is not an authorization bypass. It does not solve CAPTCHAs, use hidden account credentials, change overlay views or keep scraping blocked HTML routes. If the feed is restricted, obtain the necessary access or configure an approved feed.
- HTTPS protects transport; it does not prevent YouTube/Meta from processing or recompressing the video you send them.
- A short rolling replay buffer and selected clips reside in laptop RAM while broadcasting. The operator can explicitly export a clip to their device. OS swap/crash dumps and platforms' recording/archive settings are outside this application. Keep devices protected if footage is sensitive.

## If something leaks

Stop the relay. Revoke/rotate platform keys in their platform control rooms. Replace `RELAY_TOKEN` with a new random secret in `.env`, restart and reconnect. Remove an unauthorized device from the private network. If a secret was ever committed, deleting the current file does not remove Git history; rotate it and clean the repository history separately.

## Reporting and validation

Review `docs/VALIDATION.md` and run `npm test`. Tests cover token/session expiry and revocation, ticket replay, origins, hostile URLs, payload limits, private-file exposure, real score normalization, and actual video processing. These checks do not establish “bug free” or “unhackable” status.
